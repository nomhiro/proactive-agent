# 下書きの書き方

他チームへの影響の連絡は、`create_proposal` で kind を `impact_notice` にして下書きを作る。チームの人が承認すると、相手のチームのアシスタントに届く。相手のアシスタントは、それを自分のチームの言葉に直して人に伝える。

## 下書きに入れること

1. 何が変わったか。起点のデータ ID と、変わった値（例: 「信号 BrkPedalPos の周期が 10ms から 20ms に変わった」）
2. 相手のチームのどのデータに響くか。影響を受けるデータ ID を `trace_impact` の結果から挙げる
3. どう響くか。解析の結果があれば数値で書く（例: 「回生トルクの立ち上がりが約 15ms 遅れる見込み」）
4. 相手のチームに確かめてほしいこと。読んだ人が次に何をすればよいかがわかるように書く
5. 統合リリースや安全要求に響くなら、そのリリースと安全要求の ID

related_artifact_ids には、起点のデータ ID と影響を受けるデータ ID を入れる。to_teams には相手のチームを入れる。

## 書き方

- 短く書く。1つの下書きに1つの件だけを書く
- 相手のチームに対応を約束させる書き方をしない。「対応してください」ではなく「影響の有無を確かめてほしい」と書く
- 自分のチームの代わりに約束しない（「こちらで戻します」などと書かない）
- 推測は推測と書く。確かめたことと分けて書く

## チームへのメッセージ

`post_message` でチームに話しかけるときも、結論を先に書き、データの ID を添える。下書きの承認を求めるときは proposal_id を渡し、「承認すると、〜チームのアシスタントに届く」と書く。
