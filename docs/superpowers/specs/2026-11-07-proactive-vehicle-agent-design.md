# 車種開発プロアクティブエージェント 設計書

- 作成日: 2026-11-07
- 状態: ドラフト（制作者の承認待ち）
- 対象: Azure / Microsoft Foundry 上で動く PoC と、それを紹介するブログ記事（Zenn）

凡例: 本文中の **【制作者決定】** は制作者が会話で決めたこと、**【Claude判断】** は Claude が決めて制作者の確認を待っていること、**【実装者裁量】** は実装者に任せることを表す。

## 1. 目的と背景

### 1.1 何を作るか
自動車メーカーの「1車種の制御ソフトウェア開発」を舞台に、**頼まれる前に動くエージェント**を作る。エージェントは開発データの変化を見張り、影響を調べ、必要な人に必要なことだけを知らせる。人とは会話でやり取りする。【制作者決定】

### 1.2 なぜ作るか
- 自動車業界の人がブログを読んで「うちでもやりたい」と思うこと。これが成功の基準である。【制作者決定】
- 制御設計の現場では、要求・仕様・モデル・テストのつながり（トレーサビリティ）を追う作業が重い。ある領域の変更が他の領域に及ぼす影響も、人づての連絡に頼っていて漏れやすい。エージェントがここを見張ることに価値がある。【Claude判断、制作者が同意】

### 1.3 体験の手本
Meta の Muse と OpenAI の Dots のような、プロアクティブなアシスタントの体験を目指す。【制作者決定】両製品の発表や解説記事から取り入れる要素は次のとおり。【Claude判断】
- エージェントの方から話しかける。人とメッセージをやり取りする感覚で使える
- 画面を閉じていても裏で働き続け、何かが変わったときや承認が必要なときに戻ってくる
- 調べるのは自由だが、外に出る行動（人への連絡など）の前には必ず承認を取る
- 見張ってほしいことを会話で頼める。覚えてほしいことを覚え、「忘れて」と言えば忘れる
- いまやっている作業、予定している作業、終わった作業が見える
- 話しかける頻度を人が調整できる

両製品は個人向けである。本設計では、これを**チームと組織向け**に作り替える。

## 2. ゴール・ノンゴール・アンチゴール

### 2.1 ゴール
1. 開発データの変化から、領域をまたぐ影響をエージェントが自分で見つけ、関係するチームに知らせる様子をデモで見せられる
2. 各チームのエージェントと車種統括エージェントが連携する様子を見せられる
3. チーフエンジニアが車種全体の状況と、判断が必要なことを一目で把握できる
4. 影響の広がりを、左から右へ流れるマインドマップで視覚的に見せられる
5. 読者が `azd up` を中心にした手順で、自分の Azure サブスクリプションに同じ環境を再現できる
6. 使わないときの費用がほぼゼロに近い（使わないときは計算資源がゼロまで縮む構成）

### 2.2 ノンゴール（今回はやらない）
- 実在の開発ツール（DOORS、Polarion、codebeamer、Simulink、Jenkins、実 HILS 装置など）との接続。データは架空のものを生成する
- Microsoft Teams や Slack への通知。制作者には Microsoft 365 テナントがない【制作者決定】
- 複数車種の同時管理
- 本番運用に耐えるセキュリティ強化（閉域網、WAF など）。ただし鍵を使わない認証と最小権限は守る
- 6チームすべての作り込み（4.3 節参照）

### 2.3 アンチゴール（動いても失敗とみなすこと）
- **通知が多すぎる**：エージェントがうるさいと感じられたら失敗。知らせる価値の判断がこの PoC の中心である
- **エージェントが開発データを勝手に書き換える**：自動車の開発で受け入れてもらうには、エージェントは知らせて下書きを作るだけにとどめ、判断と実行は人が行う
- **根拠のない主張**：「影響があります」と言うときは、必ずどのデータからそう判断したかを辿れる。マップで光る枝がその証拠になる
- **読者が再現できない**：手作業の設定が多い、費用が高い、プレビュー機能の地域制限で動かない、のいずれも失敗

## 3. 舞台設定（架空のプロジェクト）

【Claude判断、制作者が同意】

### 3.1 車種とプロジェクト
- 車種: 新型 EV「架空SUV」（コンパクト SUV）
- 対象: 車両制御ソフトウェアの開発。モデルベース開発（Simulink でモデルを作り、コードを自動生成して ECU に載せる）を前提とする
- 時期: 2か月ごとにソフトを統合してリリースしている。デモ時点で次の統合リリース「R3」まで12日

### 3.2 組織
1つの車種を軸に、その下に領域ごとのチームがある。チーフエンジニアは車種全体を見る。【制作者決定】

| チーム | 役割 |
|---|---|
| 車両統合制御 | アクセル・ブレーキ操作から各 ECU への指令を決める。回生ブレーキの協調制御もここ |
| モーター制御 | 駆動モーターのトルク制御 |
| 電池制御（BMS） | 充放電と温度の管理 |
| 評価 | SILS / HILS による試験 |
| ソフト統合 | 各チームのソフトをまとめてリリースする |
| 機能安全 | ISO 26262 の安全要求の管理 |
| チーフエンジニア | 車種全体の責任者。領域をまたぐ判断をする |

### 3.3 人物（デモ用、すべて架空）
- 田中（車両統合制御、回生協調の主担当）
- 佐藤（モーター制御）
- 鈴木（評価）
- 高橋（チーフエンジニア）
- そのほか各チームに1〜2名。名前は実装者裁量

### 3.4 管理する開発データ
- 制御要求（REQ-xxx）
- 制御仕様（SPEC-xxx）
- CAN 信号定義（信号名、型、周期、送信元 ECU、受信先）
- 制御モデル（MDL-xxx、バージョン、前提とする信号と周期）
- テストケース（TC-HILS-xxx / TC-SILS-xxx）と試験結果（合否、ログ）
- 安全要求（SR-xxx）
- レビュー記録
- 統合リリース（R3 など、期日と対象）

各データは、上流のデータの ID を持つ（例: モデルは自分が満たす仕様と、使う信号の ID を持つ）。このつながりがトレーサビリティであり、影響範囲を調べる根拠になる。

## 4. エージェントの構成

### 4.1 2種類のエージェント
【制作者決定】チームごとに1体のチームアシスタントと、それらを統合する車種統括エージェントを置く。

**チームアシスタント**（領域チームごとに1体、チーム全員で共有）
- 自分のチームに関わる変化を見張り、影響を調べ、チームに知らせる
- 他チームに影響しそうなことを見つけたら、そのチームのアシスタントに知らせる
- 他チームのアシスタントから受け取った知らせを、自分のチームの文脈（担当者、進行中の作業）で解釈し直して、自分のチームに伝える
- 会話はチーム共有。チームの誰かが頼んだ見張りや、覚えさせたことはチーム全員に効く
- 外に出る行動は、チームの誰かが承認すると実行される

**車種統括エージェント**（チーフエンジニア向け、1体）
- 朝の車種ブリーフィング: 「リリースに響くリスク」「判断が必要なこと」「昨日から変わったこと」の3つに絞る
- 判断が必要なことを上げる: チーム間で利害がぶつかる場面で、両チームの言い分と選択肢を並べ、チーフエンジニアに判断を仰ぐ
- リリース判定の材料: リリース前に、未検証の要求や安全要求の抜けを車種全体で集計し、間に合うかの見立てを添える
- チーフエンジニアからの質問に、各チームのアシスタントに確認して答える

### 4.2 エージェントどうしのつなぎ方
【Claude判断】チームアシスタントどうしは直接やり取りする（網の目型）。統括エージェントはすべてのやり取りの写しを受け取って全体を把握し、次の場合だけ前に出る。
- チーム間で解決できないとき（片方が「対応できない」と返した、期限内に返事がない、など）
- リリースに響くとき（リリース対象の要求や安全要求に影響する）

理由: 統括エージェントがすべてを中継すると、そこが詰まる。チーフエンジニアも細かい連絡まで見たくはない。

やり取りの手段は用途で2つに分ける。【Claude判断】

| 用途 | 手段 | 理由 |
|---|---|---|
| 知らせる（送りっぱなしでよい） | Cosmos DB の「エージェント間メールボックス」に書き、変更フィードで相手を起動する | 相手が寝ていても届く。全件が記録に残り、統括エージェントが写しを読むのも簡単。再実行にも強い |
| 尋ねる（その場で答えが要る） | Foundry の A2A（エージェント間通信、v1.0） | 統括エージェントが「回生ブレーキまわりは今どう？」と各チームに聞いて答えをまとめる場面。同期の問い合わせに向く |

注意: Foundry の A2A は、受け側が Responses プロトコルを公開している必要がある。テキストのみで、ストリーミングには対応していない（2026-11 時点のドキュメント）。

**人の承認が要るやり取りの境目**【Claude判断】
原則: **他チームの人の目に触れるものは、発信元チームの人が承認する。** エージェントどうしの内部のやり取りは承認なしで進めてよい。

`agent_mail` の種類と承認の要否は次のとおり。

| 種類 | 例 | 承認 | 受け手のアシスタントの動き |
|---|---|---|---|
| `analysis_request` | 統合制御 → 評価「この周期変更で応答がどう変わるか Sandbox で見て」 | 不要 | 解析して結果を `analysis_result` で返す。評価チームの人には作業記録として見えるだけで、話しかけはしない |
| `analysis_result` | 評価 → 統合制御（解析結果） | 不要 | 自分の調査に取り込む |
| `question` / `answer` | 統括 → 各チーム「回生まわりの状況は？」（通常は A2A。返事を待たなくてよい場合はメール） | 不要 | 自分のチームのデータから答える。人には話しかけない |
| `impact_notice` | 統合制御 → モーター制御「この変更があなたのチームの MDL-MotorTq に影響する。確認してほしい」 | **必要**（発信元チームの誰か） | 自分のチームの文脈で解釈し直し、自分のチームの人に話しかける |
| `human_reply` | 受け手のチームの人の返答（「今週は対応しきれない」など）を発信元へ返す | 不要（人の発言そのものなので） | 発信元のチームに伝える |
| `escalation` | 各チーム → 統括（4.2 節の条件を満たしたとき） | 不要 | 統括エージェントがチーフエンジニアへの判断案件を作る |

`impact_notice` は、エージェントが下書きを `proposals` に入れる。人が承認したときに初めて、BFF が `agent_mail` に書く。エージェントが自分で `impact_notice` を `agent_mail` に書く経路は作らない（7.5 節の書き込み窓口で拒否する）。

**エージェントはチームの代わりに約束しない。** 「対応できる・できない」「いつまでにやる」といった返答は、必ず人が自分のアシスタントとの会話で行う。アシスタントはそれを `human_reply` として相手に届けるだけである。

### 4.3 PoC で作り込む範囲
【Claude判断】
- エージェントとして動かす: 車種統括、車両統合制御、モーター制御、評価 の4体
- データだけ用意する: 電池制御、機能安全、ソフト統合（マップには出るが、アシスタントは「準備中」と表示）
- 4体は同じコードから作り、チーム ID などを環境変数で切り替えて、別々のホステッドエージェントとしてデプロイする。各エージェントが専用の Entra ID と A2A のエンドポイントを持つ

## 5. 体験の設計

### 5.1 画面
【制作者決定】左から右へ流れるマインドマップを中心にする。【Claude判断】Muse / Dots 風に、会話を主役にしてマップを隣に置く。

1画面に3つの区画を並べる（ブレインストーミングで見せた案 `assistant-ux.html` に準拠）。

1. **会話**（左）
   - アシスタントが先に話しかけたメッセージと、人との会話が時系列に並ぶ
   - 承認カード: 下書きと「送る / 直す / 今回は送らない」
   - グラフなどの解析結果を添付できる
2. **影響マップ**（中央）
   - 左端が車種、右へ「領域 → 要求 → 仕様・信号 → モデル → テスト」と枝分かれする
   - 会話中のメッセージや通知を選ぶと、影響の及ぶ枝だけが赤く光り、ほかは薄くなる。変更の起点は塗りつぶし、影響を受けるものは赤枠、領域をまたぐ影響は点線で描く
   - 関係のない領域は折りたためる
   - チームの画面では自分のチームの枝が濃く、チーフエンジニアの画面では全体を均等に表示する
   - 下に「アシスタントの作業（いま / 予定 / 完了）」を表示する
3. **見張りと設定**（右）
   - 見張っていることの一覧（会話で追加・削除できる）
   - 話しかける頻度: 止める / 重要だけ / ふつう / こまめに
   - 覚えていることの一覧（「忘れて」で消せる）

画面の上部に車種名と統合リリースまでの日数を出す。チーフエンジニアの画面は、会話欄に「判断が必要な案件」を優先して並べる。

### 5.2 ログインと人物の切り替え
【Claude判断】アプリへのアクセスは Entra ID のサインインで守る。サインイン後、画面上部で「誰として見るか」（田中 / 佐藤 / 鈴木 / 高橋）を切り替えられる。ブログやデモで、同じ出来事が各チームとチーフエンジニアにどう見えるかを並べて見せるための機能である。

### 5.3 デモのシナリオ
シナリオを1手ずつ進める仕組み（管理用の画面のボタン、または CLI）を用意する。毎回同じ流れを再現できるようにし、記事のスクリーンショットや動画を撮りやすくする。【Claude判断】

**シナリオ1: CAN 信号の周期変更（領域をまたぐ影響）** ― 主役のシナリオ
1. 夜 21:10、田中が信号 BrkPedalPos の周期を 10ms から 20ms に変更する（変更イベントが登録される）
2. 統合制御のアシスタントが起動し、影響範囲を辿る。自チームの回生協調モデルとテスト5件、モーター制御のモデル MDL-MotorTq とテスト1件が影響を受けると判明する
3. 統合制御のアシスタントが、評価のアシスタントに `analysis_request` を送る（承認不要）。評価のアシスタントが Sandbox で簡易モデルを動かし、回生の立ち上がりが約15ms遅れるという結果をグラフ付きで返す
4. リリースに響くので本来は「すぐ知らせる」だが、夜間（7.4 節の静かな時間帯）なので翌朝 8:00 まで待つ。翌朝、統合制御のアシスタントが田中に話しかける。マップで影響の枝が光る。「モーター制御と評価に影響の連絡を送ってよいか」の承認カード（`impact_notice` の下書き）を出す
5. 田中が承認すると、モーター制御と評価のアシスタントに `impact_notice` が届く。モーター制御のアシスタントは「佐藤さんが今週 MDL-MotorTq v2.1 を作業中」という文脈を添えて佐藤に話しかける
6. 佐藤がアシスタントに「今週は v2.1 で手一杯で、R3 までに 20ms 対応は無理」と返す。これが `human_reply` として統合制御に届く。田中も自分のアシスタントに「周期は CAN 負荷の都合で戻せない」と返す。双方の人が「できない」と言ったので（4.2 節の条件）、各チームのアシスタントが `escalation` を送り、統括エージェントが判断案件としてチーフエンジニアの高橋に上げる。両チームの言い分と選択肢（周期を戻す / モデルを直す / R3 から外す）を並べる

シナリオ中の人の発言（手順6の佐藤と田中の返答など）は、シナリオを進める仕組みが会話として投入する。人の発言は台本どおり、エージェントの応答は毎回本物の LLM が作る。

**シナリオ2: HILS の失敗傾向**
1. 回生協調の HILS 試験が3回続けて失敗する
2. 評価のアシスタントが Sandbox で失敗ログを解析する。直近のモデル変更（MDL-RegenCoord v1.8）と結びつける
3. 「回生協調の HILS 失敗はすぐ知らせて」という見張りがあるので、朝を待たずにすぐ知らせる

**シナリオ3: 朝のブリーフィング**
- チームごとに、今日の期限、遅れているタスク、昨日からの変化をまとめて届ける
- チーフエンジニアには、車種全体のリスク、判断が必要なこと、変化の3点に絞って届ける

**シナリオ4: リリース前の抜け漏れチェック**
- 統合リリースの1週間前に、未検証の要求、未完了のレビュー、検証の済んでいない安全要求を車種全体で集計する。間に合うかの見立てを添えて、チーフエンジニアと関係チームに届ける

**シナリオ5: 会話で見張りを頼む・忘れさせる**
- 「回生協調の HILS が落ちたらすぐ教えて」→ 見張りの一覧に加わる
- 「連絡は朝まとめて」→ チームの好みとして覚える
- 「さっきの好みは忘れて」→ 消える

```
        │   ┌────────────────────────────────────────┐
        └───│ Azure Functions                          │
            │ ・変更の振り分け（どのチームに関係するか）   │
            │ ・まとめ（短時間の連続変更を1回にする）      │
            │ ・定時実行（朝のまとめ、リリース前チェック）   │
            │ ・エージェント間メールボックスの配達          │
            └────────────────────────────────────────┘
```

### 6.2 各サービスの役割と選んだ理由

| サービス | 役割 | 選んだ理由 |
|---|---|---|
| **Foundry ホステッドエージェント**（Python、Microsoft Agent Framework） | 4体のエージェント本体 | 影響範囲を辿る処理は自前のコードの方が確実。各エージェントに専用の Entra ID が付くので、キーを使わずに権限を絞れる。Responses / Invocations / A2A を同時に公開できる。セッションごとに隔離された環境で動き、使わないときはゼロまで縮む |
| **Azure Functions**（Flex Consumption、Python） | 変更フィードのトリガー、定時実行、メールボックスの配達、エージェント用の書き込み窓口（7.5 節） | Cosmos DB の変更フィードを最も簡単に受けられる。LLM を呼ぶ前に、意味のある変更だけに絞る門番になる |
| **Cosmos DB for NoSQL**（サーバーレス） | 開発データ、通知、提案、監査記録などすべての保存先 | 変更フィードで「データが変わったら動く」を実現できる。エンティティ単位の JSON が自然に収まる |
| **Container Apps Sandboxes** | エージェントが書いた解析コードの実行 | 外部通信を止めた隔離環境で、生成コードを安全に動かせる。制御工学向けライブラリ入りのイメージを持ち込める。一時停止と再開ができ、調査の続きを後日再開できる。【Claude判断】Foundry 標準のコードインタープリターより手間はかかるが、「ここまでできる」と読者に見せる価値を優先した |
| **Foundry Memory**（プレビュー） | チームの好みや会話の要約を長期に覚える | scope をチーム ID にすれば、チーム単位の記憶になる。「覚えて」「忘れて」の直接指示に対応している |
| **Container Apps**（Web アプリ） | 画面と API（BFF） | エージェント群と同じ Container Apps 環境にまとめられる。Entra ID の組み込み認証が使える |
| **Azure Web PubSub** | エージェントからブラウザへのリアルタイム通知 | アシスタントが先に話しかける体験には、画面を開いている人へ即座に届ける仕組みが要る。Functions から出力バインドで送れる |
| **Blob Storage** | HILS ログ、解析で作ったグラフ画像 | Sandboxes のボリュームとして直接マウントできる |
| **Application Insights** | トレースと監視 | ホステッドエージェントは接続文字列が自動で注入され、OpenTelemetry のトレースが出る |
| **Azure Developer CLI（azd）+ Bicep** | 一式のデプロイ | 読者が再現しやすい。ホステッドエージェントも azd でデプロイできる |

【実装者裁量】Web アプリの画面の技術（React など）。ただし日本語 UI であること。

### 6.3 地域
ホステッドエージェント、Foundry Memory、Container Apps Sandboxes、Web PubSub がすべて使える1つの地域を選ぶ。実装者は着手時に各サービスの提供地域を確認し、選んだ地域と理由を README に書く。すべてがそろう地域がない場合は制作者に相談する。

## 7. 仕組みの詳細

### 7.1 基本の考え方
【Claude判断】**決まった手順で求まるものはコードで求め、判断と説明だけを LLM に任せる。**
- 影響範囲（どのデータがどのデータに依存しているか）はグラフを辿るコードで求める。LLM には辿らせない
- LLM が担うのは次の3つ: 影響の重さの判断、知らせる価値があるかの判断、人にわかる説明と下書きの作成
- こうすることで、主張の根拠（マップで光る枝）が常にデータと一致する

### 7.2 データの保存（Cosmos DB）
データベースは1つ。主なコンテナと役割は次のとおり。パーティションキーは原則 `/vehicleId`（PoC は1車種なので実質1つ）。件数は数百程度を想定する。

| コンテナ | 中身 | 書く人 |
|---|---|---|
| `artifacts` | 要求・仕様・信号・モデル・テストケース・安全要求・リリースの最新版。各文書に `type`、`team`、`owner`、`version`、`links`（上流の ID の配列）を持たせる | シナリオ再生、（将来）外部ツール連携 |
| `change_events` | 変更の記録（追記のみ）。変更前と変更後の値、変更した人、日時を持つ。**変更フィードの監視対象はこのコンテナ** | シナリオ再生 |
| `test_runs` | 試験結果（合否、ログの Blob の場所） | シナリオ再生 |
| `watches` | 見張りの条件（チーム、対象、条件、即時かまとめてか）。構造化データとして持つ | エージェント（会話で頼まれたとき） |
| `messages` | 画面の会話欄に出すメッセージ（アシスタントが先に話しかけたもの、会話、承認カード） | エージェント、BFF |
| `proposals` | 承認待ちの行動（下書き、宛先、状態） | エージェントが作り、BFF が実行 |
| `agent_mail` | エージェント間メールボックス（送り手、宛先、種類、本文、関連データ ID） | エージェント（承認後は BFF） |
| `notifications` | 影響の分析結果。起点のデータ、影響を受けるデータの一覧、領域をまたぐつながり。マップを光らせる根拠になる | エージェント |
| `agent_runs` | エージェントの作業記録（いま / 予定 / 完了、使ったツール、Sandbox の実行） | エージェント |
| `schedules` | 定時の仕事と、エージェントが自分で入れた「後でもう一度確認する」予定 | Functions、エージェント |
| `team_settings` | 話しかける頻度、チームのメンバーと役割 | BFF |
| `leases` | Functions の変更フィード用 | Functions |

変更フィードの標準モードは変更前の値を返さない。そのため、変更前と変更後を持つ `change_events` を監視対象にした。

### 7.3 頼まれる前に動くための3つのきっかけ

**(1) データが変わったとき**
1. `change_events` に変更が書かれる
2. Functions の振り分け処理が起動する。LLM は使わずに次を求める
   - 変更されたデータから下流を辿り、影響を受けるデータとチームを求める
   - そのチームの見張り条件に合うかを調べる
3. 関係するチームごとに「調査の依頼」を作る。短い時間に同じデータが何度も変わったら、1回の依頼にまとめる（目安は2〜5分）【実装者裁量: まとめ方の実装】
4. 依頼を、そのチームのアシスタントにバックグラウンド実行で渡す
5. 同じ変更で2回起動しても通知が二重にならないよう、依頼に変更イベントの ID から作った冪等キーを付ける

**(2) 時刻になったとき**
- 毎朝 8:00（日本時間）: チームごとの朝のまとめ、車種統括のブリーフィング
- 統合リリースの7日前の朝: 抜け漏れチェック
- エージェントが自分で入れた予定（例: 「明日、再試験の結果をもう一度見る」）。`schedules` に入れておき、定時の処理が拾う

**(3) 他のエージェントから知らせが届いたとき**
- `agent_mail` に書かれると、変更フィードで Functions が起動し、宛先のアシスタントを起動する
- 統括エージェントには全件の写しが届く。ただし統括エージェントが前に出るのは 4.2 節の条件のときだけ

### 7.4 知らせるかどうかの判断
エージェントは調査の最後に、結果を次の3つのどれにするかを決める。【Claude判断】
- **すぐ知らせる**: リリースに響く、安全要求に関わる、即時の見張り条件に合う
- **朝のまとめに入れる**: 知っておくべきだが急ぎではない
- **知らせない**: 影響が小さい、すでに対応済み。ただし作業記録には残す

判断の材料: 影響の大きさ、リリースまでの日数、チームの話しかける頻度の設定、チームの好み（記憶）、同じ件をすでに知らせたか。
判断の理由は作業記録に残し、画面の「完了」から見られるようにする。

**静かな時間帯**【Claude判断】
20:00〜翌 7:59（日本時間）は「すぐ知らせる」に分類したものも保留し、翌朝 8:00 に、朝のまとめより先に個別のメッセージとして届ける。ただし安全要求に関わるものだけは時間帯に関係なく即時に届ける。調査そのものは夜間も進める（Muse / Dots の「寝ている間に働く」）。時間帯はチームの設定で変えられる。

**仮想の時計**
「翌朝」「7日前」「毎朝 8:00」をデモで再現するため、システム全体が参照する現在時刻を差し替えられるようにする（シナリオを進める仕組みが時計を進める）。

### 7.5 承認と安全の仕組み
【Claude判断】Muse の Sentinel にならい、「エージェントは提案するだけで、実行は人の承認後に決まったコードが行う」という線引きを、仕組みで強制する。

Cosmos DB のデータ操作の権限（RBAC）は、コンテナ単位が最も細かい。そのため「種類」や「宛先チーム」の制限は権限だけでは強制できない。そこで次の2段構えにする。

1. **エージェントの Entra ID には、Cosmos DB の読み取り権限だけを与える。** 書き込み権限は一切与えない
2. **書き込みはすべて「書き込み窓口」を通す。** 書き込み窓口は Functions の HTTP 関数で、エージェントの Entra ID で認証する。呼び出し元のエージェントがどのチームのものかをトークンから判定し、次を検査してから書く
   - 書ける対象: 自チームの `messages`、`proposals`、`notifications`、`agent_runs`、`watches`、`schedules`
   - `agent_mail`: 承認不要の種類（4.2 節の表）だけ。`impact_notice` は拒否する
   - 他チームの宛先への `messages` / `proposals` は拒否する
   - `artifacts`、`change_events`、`test_runs` への書き込みは常に拒否する

記事では「エージェントには書き込み権限が一切なく、書き込みは検査付きの窓口だけ」と書ける。

- 人への連絡、他チームへの `impact_notice` は必ず `proposals` に下書きとして入れる。人が画面で承認すると、BFF が実行する（BFF の ID には必要な書き込み権限を与える）
- 承認なしで実行してよい行動を、チームが事前に許可できる（例: 朝のまとめの配信）。Dots の「繰り返しの低リスクな行動は事前に承認できる」にならう
- Sandbox は外部への通信を止める。読めるのは調査に必要な Blob のボリュームだけにする

### 7.6 解析（Container Apps Sandboxes）
- 制御工学向けのライブラリ（numpy、pandas、scipy、python-control、matplotlib）を入れたイメージを用意し、Sandbox のディスクイメージとして登録する
- 調査1件につき Sandbox を1つ作る。HILS のログを入れた Blob のボリュームをマウントし、エージェントが書いた解析コードを実行する。グラフは Blob に保存し、会話にそのグラフを添付する
- 調査が終わったら一時停止する。数日後に自動で削除する
- 回生協調の簡易モデル（数式で書いた一次遅れ程度の単純なもの）を用意する。「信号の周期が変わると応答がどれだけ遅れるか」を再現する。モデルの中身は【実装者裁量】。ただし結果がシナリオ1の筋書き（約15ms の遅れ）と矛盾しないこと
- 評価チームのアシスタントが Sandbox を使う役を担う。他チームのアシスタントは、評価のアシスタントに解析を依頼する

### 7.7 記憶
- **Foundry Memory**（チームの好み、会話の要約）: scope はチーム ID。「覚えて」「忘れて」の直接指示を使う
- **見張り条件**: Functions が LLM なしで判定する必要があるので、Memory ではなく `watches` に構造化して保存する。エージェントは会話で頼まれたら `watches` に書く
- 画面の「覚えていること」には、Memory の項目と `watches` を並べて出す

### 7.8 会話
- 画面からの会話は、各アシスタントの Responses プロトコルで行う。会話の ID はチームごとに1本持ち、チーム全員で共有する
- アシスタントが先に話しかけたメッセージも会話欄に並べる必要がある。そのため、画面に出すものの正本は `messages` コンテナとし、BFF が会話の応答も `messages` に書き写す
- 新しいメッセージは Web PubSub で画面に即座に届ける

### 7.9 作業の見える化
- `agent_runs` に、作業の開始、使ったツール、Sandbox の実行、判断の結果、終了を記録する
- 画面の「いま / 予定 / 完了」はここから作る。「予定」は `schedules` から作る
- Application Insights のトレースと、`agent_runs` の ID を対応づける

## 9. 品質の確かめ方
【Claude判断】デモもシナリオテストも本物の LLM で動かす。記録した応答を再生する仕組みは作らない。LLM の文章は毎回変わってよい。合否は構造化された結果で判定する。
- **単体テスト**: 影響範囲の計算、振り分け、まとめ、冪等性、書き込み窓口の検査はコードなので、通常の単体テストで確かめる
- **シナリオテスト**: 5つのシナリオを最初から再生し、次を確かめる
  - 影響を受けるデータの集合（＝マップの光り方）が期待どおりであること（コードで決まるので完全一致）
  - 知らせるかどうかの3分類が期待どおりであること
  - 承認カードが出るべき場面で出ること、エスカレーションが起きるべき場面で起きること
  - 文章の中身は判定しない。ただし起点のデータ ID と影響を受けるデータ ID に触れているかは確かめる
- **通知の質**: 「知らせるべきでない変更」（影響のない軽微な変更、すでに対応済みの件）をシナリオに混ぜる。エージェントが黙っていられるかを確かめる。アンチゴール「通知が多すぎる」への対策
- **二重通知がないこと**: 同じ変更イベントを2回流しても、通知が1回であることを確かめる
- **権限**: エージェントの ID で Cosmos DB に直接書こうとすると拒否されること、書き込み窓口で `impact_notice` や他チーム宛ての書き込みが拒否されることを確かめる
